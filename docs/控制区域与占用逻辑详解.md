# 控制区域（ControlArea）与占用逻辑详解

> 本文是红绿灯系统**占用/放行**原理的深度解析：ControlArea 是什么、放在哪、Locker/Group/ControlArea 三级怎么配合、AGV 为什么会被拦住、代码里每个动作在干什么。
> 配套教程见 [占用模块](占用模块.md)，配时计算方法见 [配时逻辑与标签详解](配时逻辑与标签详解.md)。

---

## 1. 为什么需要它：灯不拦车，ControlArea 才拦车

FlexSim 的 AGV 只认**路径**，不认"红绿灯"——没有控制的话，两个方向的 AGV 在路口会直接对冲穿行。红绿灯实体只是视觉指示，**真正让 AGV 停下来的，是铺在路径上的 ControlArea（控制区域）**：

- ControlArea 是 FlexSim AGV 路网内置的"控制区"，铺在 AGV 路径上，是一个矩形停车/禁行区；
- **任何 AGV 要进入 ControlArea，必须先获得"占用许可"**；拿不到许可就在区域外等待；
- 谁给许可？由我们（红绿灯逻辑）通过 **Locker** 统一控制：锁定 = 不给许可（禁行），解锁 = 给许可（放行）。

## 2. ControlArea 放在哪（位置规则）

**位置：每个方向进口道的"停车线"处——即进入路口冲突区之前的那段路径上。**

```
                ▲ 北
                │
   ┌────────────┼────────────┐
   │  NS 停车区   │  (南北方向    │
   │  ControlArea│  ControlArea)│
   │  ╔══════════╪══════════╗  │
───┼──╢   路口冲突区      ╠──┼──► 东
   │  ╚══════════╪══════════╝  │
   │  EW 停车区   │  (东西方向    │
   │  ControlArea│  ControlArea)│
   └────────────┼────────────┘
                ▼
               南
```

| 方向组 | ControlArea 位置 | 归入 Group |
|--------|------------------|------------|
| 南北（NS） | 南北进口道、冲突区**之前**的路径段（停车线处） | `NS_Stop_CA_Group` |
| 东西（EW） | 东西进口道、冲突区**之前**的路径段（停车线处） | `EW_Stop_CA_Group` |
| 右转（不受控） | **不放** ControlArea | — |

要点：

- ControlArea 必须放在**冲突区之外**：停在里面的 AGV 不会堵住交叉口本身；
- 一个方向路径较长时可以放**多个** ControlArea，全部归入该方向的 Group；
- 一个 ControlArea 只归入一个 Group（避免方向间互锁冲突）；
- 右转不受控方向不放 ControlArea（右转在多个相位都有窗口，始终自由）。

## 3. 三级结构：Locker / Group / ControlArea

| 组件 | 类型 | 作用 |
|------|------|------|
| `ControlArea` | AGV 路网对象 | 停车区本体；AGV 进入前必须获得占用许可 |
| `Group` | Toolbox 对象 | 把某一方向的所有 ControlArea 归为一组 |
| `Locker` | AGV Resource（Resource 类） | 以"占用者"身份对一组 ControlArea 统一加锁/解锁 |

对应关系（一个方向一套）：

```
Locker（锁）  ──►  Group（组）  ──►  ControlArea × N（停车区们）
  TrafficLightLocker_NS    NS_Stop_CA_Group    NS 方向所有 ControlArea
  TrafficLightLocker_EW    EW_Stop_CA_Group    EW 方向所有 ControlArea
```

## 4. 底层机制：AllocatableObject 的 allocations / requests

ControlArea 实现了 `AGV.AllocatableObject` 接口，它身上挂着两个列表：

| 列表 | 含义 |
|------|------|
| `allocations[]` | **当前已占用**列表，每个元素是一个 `AllocationPoint`（谁占着这个区域） |
| `requests[]` | **排队等待**列表（谁在申请但还没拿到） |

每个 `AllocationPoint` 都有一个 `allocator`（占用者身份）。我们的 Locker 就扮演这个"占用者"：

- `ca.allocate(locker, 1)` —— Locker 申请占用 ControlArea → 进入 allocations（已锁定）；
- `ap.deallocate()` —— 释放一个 AllocationPoint（注意：这个方法在 `AllocationPoint` 上，**不在** `AllocatableObject` 上）。

**AGV 视角**：AGV 接近 ControlArea 时会自动请求占用；如果区域已被 Locker 锁定（allocations 里有 locker 的占用），AGV 就拿不到许可，在区域前停车排队（进入 requests）。解锁后，等待中的 AGV 依次获得许可通过。

## 5. 完整工作流程（时序）

```
模型启动
  │  初始化脚本：所有方向 Locker 先锁住各自 Group 内全部 ControlArea（预锁红灯）
  ▼   → 任何 AGV 都进不了路口
灯状态机轮转（phase 标签 + senddelayedmessage，各灯按偏移时间错开）
  │
  ├─ 某灯离开 GREEN（变黄）→ 锁定本方向：该方向全部 ControlArea allocate
  │    → 新来的 AGV 在停车线外排队
  ├─ 某灯进入 GREEN → 释放本方向：locker 名下的 allocations/requests 全部 deallocate
  │    → AGV 获准进入并通过路口

  ▼    → 下一个方向再放行
```

**两个动作的时机**（以灯实体 OnMessage 为例）：

| 动作 | 触发时机 | 代码做什么 |
|------|----------|-----------|
| **锁定** | `state == "GREEN"`（即离开绿灯、进入黄灯） | 遍历本方向 Group，对每个 ControlArea 检查是否已锁，未锁则 `ca.allocate(locker, 1)` |
| **释放** | `nextState == "GREEN"`（即刚进入绿灯） | 遍历本方向 Group，倒序遍历 `allocations`/`requests`，把 `locker` 名下的 `AllocationPoint` 全部 `ap.deallocate()` |

> 为什么黄灯就开始锁？黄灯期间新来的车不应该再进路口，但已经在路口里的车还有时间清空。这就是"离开 GREEN 锁、进入 GREEN 放"的原因。

**防重锁检查**（`alreadyLocked`）：初始化脚本已经锁过一遍，状态切换时再锁，必须先用名称比较判断"是否已被本 Locker 锁过"，否则同一个 ControlArea 会被锁定两次，释放时也会释放两次。

## 6. 双保险：OnMessage 直控 + ProcessFlow 轮询

两个方向组互锁（任意时刻只有 1 个方向 GREEN）靠的是**相位错开**（见 [配时逻辑与标签详解](配时逻辑与标签详解.md)），而占用动作有两条实现路径，结果一致：

| 实现路径 | 说明 |
|----------|------|
| **灯实体 OnMessage 直控** | 通过 `lockerName`/`groupName` 指针标签直接锁/放；可与 ProcessFlow 组成双保险 |
| **ProcessFlow 子流程轮询** | 死循环轮询 `phase` 标签，GREEN → deallocate，变红 → allocate；独立运行、容错强 |

- OnMessage 直控：与状态机耦合紧密、实时性好，但一旦占用逻辑抛异常会连带影响消息循环（见坑 1）；
- ProcessFlow 轮询：独立运行、容错强，即使某个灯的消息异常，PF 也会按 `phase` 标签兜底；
- 两者都执行同一件事：**绿灯放行、红灯锁定**，同时跑也不会冲突（锁/放是幂等的）。

## 7. 状态机与占用的对应关系

```
GREEN ──黄闪──► YELLOW ──红灯──► RED ──绿灯──► GREEN
  │               │                        │
  ▼               ▼                        ▼
 释放本方向     锁定本方向                保持锁定
 AGV 通行       AGV 禁行                 AGV 禁行
```

| phase | 灯色 | 占用动作 | AGV 行为 |
|-------|------|----------|----------|
| GREEN | 🟢 | 释放本方向 | 通行 |
| YELLOW | 🟡 | 锁定本方向 | 禁行（减速停车） |
| ALLRED | 🔴 | 保持锁定 | 禁行（清空冲突区） |
| RED | 🔴 | 保持锁定 | 禁行 |
| YELLOW2 | 🟡 | 保持锁定 | 禁行 |
| 复位 | ⚪ 灰 | — | — |

## 8. 代码实现的关键细节与坑

> 全部来自实际踩坑（详见 [踩坑记录](踩坑记录.md)），照着写能绕开大部分问题：

1. **`senddelayedmessage` 必须放在占用逻辑之前** —— 占用逻辑一旦抛异常，后面的消息发送就执行不到，消息循环断裂、灯永远不变色；
2. **遍历 Group 用 `Group(grp.name)[i]` 成员索引，不用 `subnodes`** —— `subnodes` 会包含 FlexSim 内部节点，强转 `AGV.AllocatableObject` 时 `Invalid down cast` 崩溃；
3. **`deallocate` 在 `AllocationPoint` 上调用**（`ap.deallocate()`），`AllocatableObject` 上没有这个方法；
4. **判断"是否已锁定"用名称比较** `string(ap.allocator.name) == locker.name`，**不要用 `==` 引用比较** —— 指针标签取到的引用和 `Model.find()` 取到的不是同一内存引用，`==` 永远 false，防重锁失效；
5. **释放时倒序遍历**（`j--`）—— `deallocate()` 会缩短数组长度，正序遍历会跳过元素；
6. **初始化脚本里 `Model.find` 名称必须完全一致**（大小写敏感），找不到对象会 `return 0` 跳过且无报错，导致启动瞬间 AGV 闯进路口；
7. **`lockerName`/`groupName` 指针标签类型必须选 Pointer**，并把 Locker / Group 拖进去绑定。

## 9. 怎么验证占用逻辑是否正确

1. 运行模型，观察：绿灯方向 AGV 能通过路口；红灯方向 AGV 在 ControlArea（停车线）前排队；
2. 控制台输出：进入 GREEN 有放行日志、变红有锁定日志，且**同一个 ControlArea 不会重复锁/放**；
3. 单灯测试：先只放一个灯，确认变色循环和占用动作；
4. 检查"同一时刻只有 1 个方向 GREEN"（偏移时间校验，见 [配时逻辑与标签详解](配时逻辑与标签详解.md)）。
